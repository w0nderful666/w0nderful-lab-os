## 不是新技术，而是新工作流

用 AI 写代码不是什么新鲜事。但把 AI 当成「并肩工作的开发者」而不是「代码生成器」来用，是过去一年我最大的转变。

> AI Agent 的真正价值不在于「写得快」，而在于「改得准」。

对于一个持续迭代的个人项目来说，改代码比写代码的频率高得多。而改代码最怕的是「改错地方」——改一个 bug 引出三个新 bug，或者改了样式导致布局崩塌。

下面是我在 w0nderful-lab-os 项目中总结的经验。

---

## 经验一：提示词要定边界

最开始的几个月，我的提示词很松散：

> 「把这个页面改成暗色主题。」

AI 响应很积极，一口气改了 20 个文件。结果：

- 样式覆盖过度，很多地方变得不可读
- 某个组件的颜色变量没改到，页面上出现一半亮一半暗的奇观
- 主题切换逻辑被意外删掉，导致无法切换回来

后来我学乖了，提示词变成了这样：

> 「在 `src/styles/os-theme.css` 的 `.theme-dark` 类中，将 `--surface-base` 从 `#eef5f0` 改为 `#0a1612`。只改这一处，不要动其他文件。」

**定边界**意味着：

1. **指定文件**：不要让 AI 自己猜
2. **指定范围**：只改必要的部分
3. **指定格式**：如果有模板，按模板来

这其实和 Code Review 是一个道理——**范围越小，错误越少**。

---

## 经验二：不能无限加功能

这是最常见的失控场景：

> User: 「能不能加一个博客搜索功能？」
> AI: 「可以，我来实现。」

一周后，页面上多了搜索框、全文索引、结果高亮、过滤选项。然后发现：

- 搜索需要加载额外的数据文件，页面首屏变慢了
- 搜索结果页的布局和 Blog 列表页不一致
- 某些关键词搜不到，因为分词逻辑有问题

我意识到：**功能是有代价的。**

每一次加功能，都意味着：

1. 更多代码要维护
2. 更多样式要覆盖
3. 更多边界情况要处理
4. 更多测试要通过

> 「一个完美的产品，是懂得说『不』的产品。」

现在加功能之前，我会先问自己三个问题：

1. **有没有现成方案？** 能用 CSS 解决的，不写 JS；能用现成组件的，不手写。
2. **三个月后我还会用它吗？** 很多「酷功能」其实只是一时兴起。
3. **它会影响现有功能的稳定性吗？** 如果会，先打住。

## 经验三：Design System Contract 是必要的

v0.8 的中期，我开始意识到一个问题：AI 每次改样式都可能打破一致性。

比如：

- Button 组件有时用 `#a8c8bd`，有时用 `var(--surface-raised)`
- 间距有时用 `16px`，有时用 `1rem`
- 圆角有时写 `4px`，有时写 `0.25rem`

这些「不一致」单独看没问题，积累起来就是灾难。

解决方案是建立 **Design System Contract**：

```markdown
# OS Design System Contract

## 颜色

- 主色调：`--accent`
- 强调色：`--accent-text` (用于 accent 背景上的文字)
- 禁用硬编码颜色，如 #07120f、#a8c8bd

## 间距

- 基础单位：`--space-sm` = 0.5rem = 8px
- 组件内边距：`--space-md` = 1rem
- 页面边距：`--space-lg` = 2rem

## 动画

- 快速切换：150ms
- 常规过渡：250ms
- 慢速/电影感：400ms+
```

这个文档不需要多正式，但必须**存在且可引用**。

现在每次让 AI 改样式，我会先说：

> 「参考 docs/OS_DESIGN_SYSTEM.md，使用 Token 而不是硬编码颜色。」

AI 执行的一致性大幅提升。

## 经验四：测试门禁必须保留

这是我踩过最大的坑。

有一段时间我让 AI 随意修改，最后直接 push 到生产环境。结果是：

- 某个 commit 把 `npm run build` 搞坏了，后面的 CI 全挂
- 某个改动导致 TypeScript 报错，但被 commit 了
- 某个 CSS 改动让移动端布局完全错乱，但我在电脑上看不出来

**测试不是可选的，它是「人类审查」的替代品。**

我的做法是：

| 测试 | 工具 | 作用 |
|------|------|------|
| 构建测试 | `npm run build` | 确认项目能编译 |
| 类型检查 | `npm run check` | 确认 TS 无错 |
| 功能自测 | `npm run self-test` | 确认核心交互正常 |
| 代码规范 | `npm run preflight` | 确认无硬编码、无 Token 遗漏 |

这四道门禁我称为 **CI 四大金刚才**。任何一次 push 前必须全部通过。

> AI 生成代码的质量波动很大，但测试不会说谎。

## 经验五：截图比口头描述更适合 UI 问题

早期我经常这样描述问题：

> 「Detail Panel 的动画看起来不自然，你调一下。」

AI 响应：

> 「我已经调整了 transition 时长从 200ms 到 300ms。」

但我看了之后说：「还是不对，感觉是曲线的问题。」AI 又改了一次，还是不对。来回折腾很久。

后来我学乖了：

> 「看这个截图，当前 Detail Panel 进入时是线性淡入。我希望它是 ease-out 并且带轻微 overshoot。请修改 `src/styles/motion.css` 中的 `.detail-panel` 动画。」

附带截图。

效果完全不同。AI 能精准理解「哪里有问题」和「改成什么样」。

## 经验六：持续沟通比一次性提示更重要

我试过一次性给 AI 一个完整的需求文档，让它全部实现。结果往往是：

- 实现到一半发现某些需求冲突
- 优先级判断错误，先做了不重要的功能
- 中间某个环节需要人工确认，但 AI 不知道

现在我更倾向于 **小步快跑**：

1. 描述一个最小需求
2. AI 实现
3. 我验证效果
4. 反馈 + 调整
5. 下一个最小需求

这种方式虽然看起来「慢」，但实际上：

- 返工率更低
- 方向更容易校正
- 成就感更持续

## 小结

用 AI Agent 做 Web 项目的这一年，我最大的感受是：

> **AI 不是替代者，它是放大器。**

用得好，效率翻倍；用得差，麻烦翻倍。

关键不在于 AI 本身，而在于你**如何设计工作流**：

- 提示词定边界，别让 AI 猜
- 功能要克制，别滥用「能做」
- Design System 是契约，照着来
- 测试是门禁，别跳过
- UI 问题用截图，别用形容词
- 持续沟通，别一次性给太多

w0nderful-lab-os 从 v0.6 到 v0.8，经历了 100+ 次 commit。其中相当一部分是 AI 辅助完成的。但核心决策始终是我做的——因为只有我知道这个产品「应该是什么样子」。

AI 负责执行，我负责定义。
